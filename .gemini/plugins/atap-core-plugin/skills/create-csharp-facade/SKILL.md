# Create C# Facade Project

Restructure a flat ATAP C# project into a **parent facade plus child
subprojects**, without changing the identity that consumers reference.

## What a facade is, and why the shape matters

In a flat ATAP project, one `.csproj` owns everything: interfaces, model
classes, string constants, enumerations, default configuration, and shim
adapters all compile into a single assembly. That works until two things start
to hurt — consumers who only need the interface contract are forced to take a
dependency on the whole implementation, and unrelated concerns inside the
assembly start referencing each other because nothing stops them.

The facade layout fixes both by splitting the concerns into separate assemblies
that live as **subdirectories of the original project directory**, and rewriting
the original `.csproj` into a nearly-empty shell whose only job is to reference
those children:

```text
src/ATAP.Utilities.Loader/
  ATAP.Utilities.Loader.csproj          <- the facade (same path, same name)
  Interfaces/
    ATAP.Utilities.Loader.Interfaces.csproj
  Model/
    ATAP.Utilities.Loader.Model.csproj
  StringConstants/
    ATAP.Utilities.Loader.StringConstants.csproj
```

The critical property is that `src/ATAP.Utilities.Loader/ATAP.Utilities.Loader.csproj`
still exists at the same path with the same name. Every consumer that already
wrote `<ProjectReference Include="..\ATAP.Utilities.Loader\ATAP.Utilities.Loader.csproj" />`
keeps working untouched. The facade absorbs the churn so the rest of the
repository does not have to. If you find yourself renaming or relocating the
parent `.csproj`, you have left the facade pattern and are doing a plain
rename — stop and reconsider, because that is the change that breaks callers.

A second property matters just as much: consumers who want a *narrower*
dependency can now reference a child directly. That is the payoff, and it only
exists because the children are real, independently referenceable projects
rather than folders inside one assembly.

## Before you edit anything

Read `references/facade-patterns.md` for the annotated before/after `.csproj`
pairs drawn from the commit that established this pattern in ATAP.Utilities
(`39f5e28da`). It shows the real Loader, Secrets, PluginDemo, and ManimDemo
conversions, including the two MSBuild failure modes that bite. Read it before
writing your first `.csproj` — the properties involved are non-obvious and
getting one wrong produces a build that either silently double-compiles or
fails with an SDK error whose message points somewhere unhelpful.

Then establish the ground truth for the specific project you are converting:

1. **Inventory the source files** in the project directory and decide which
   child each belongs to. The file names usually tell you: `StringConstants.cs`
   → `StringConstants/`, `DefaultConfiguration.cs` → `DefaultConfiguration/`,
   the primary implementation → `Model/`.
2. **Find sibling projects that belong inside.** A flat `src/X.Interfaces/`
   next to `src/X/` is the single strongest signal — it is a child that was
   never given a home. It becomes `src/X/Interfaces/`.
3. **Find every consumer.** Search the whole repo, `src/` and `tests/` alike,
   for `ProjectReference` lines naming the project or any sibling you are about
   to absorb. Those absorbed siblings' paths are about to go stale everywhere.
4. **Read `Directory.Build.props`.** ATAP centralizes `TargetFramework` there.
   Child projects inherit it; do not restate it.

## Building the facade

### The facade `.csproj`

Rewrite the original file in place. Keep its version and packaging properties —
they carry the project's published identity and resetting them silently changes
what NuGet emits. Drop everything else: package references, compile items, and
the project references that now belong to a child.

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Library</OutputType>
    <!-- NO TargetFramework/TargetFrameworks here — inherited from Directory.Build.props -->
    <GeneratePackageOnBuild>true</GeneratePackageOnBuild>
    <IsPackable>true</IsPackable>
    <MajorVersion>0</MajorVersion>
    <MinorVersion>1</MinorVersion>
    <PatchVersion>0</PatchVersion>
    <PackageLifeCycleStage>Development</PackageLifeCycleStage>
    <PackageLabel>Alpha</PackageLabel>
    <EnableDefaultItems>false</EnableDefaultItems>
  </PropertyGroup>

  <ItemGroup>
    <ProjectReference Include="Interfaces\ATAP.Utilities.Loader.Interfaces.csproj" />
    <ProjectReference Include="Model\ATAP.Utilities.Loader.Model.csproj" />
    <ProjectReference Include="StringConstants\ATAP.Utilities.Loader.StringConstants.csproj" />
  </ItemGroup>
</Project>
```

`EnableDefaultItems=false` is the load-bearing line. The SDK's default compile
glob is `**/*.cs` rooted at the project directory — and the children are now
*inside* that directory. Leave the glob on and the facade compiles every child's
sources into itself while the children compile them again, producing duplicate
types across assemblies. The symptom is confusing (ambiguous-reference errors in
consumers, or a build that succeeds and misbehaves at runtime), so set the
property as a matter of course on every facade rather than waiting for it to
break.

Turning the glob off means the facade no longer picks up files you genuinely
want to keep at the parent level. Add those back explicitly:

```xml
<ItemGroup>
  <Compile Include="Properties\AssemblyInfo.cs" />
</ItemGroup>
```

### Cross-cutting build infrastructure stays on the facade

Weaving and diagnostics infrastructure applies to the whole project family, so
it belongs on the facade rather than being copied into each child:

```xml
<!-- Packages and projects to implement IL Weaving using Fody during the build process -->
<ItemGroup>
  <PackageReference Include="MethodBoundaryAspect.Fody" />
  <ProjectReference Include="..\ATAP.Utilities.ETW\ATAP.Utilities.ETW.csproj" />
</ItemGroup>
```

### Child `.csproj` files

Each child is an ordinary, complete project — not a fragment. It carries its own
version and lifecycle properties, its own `PackageReference` set, and its own
project references. Give each child the version and `PackageLifeCycleStage` that
honestly describes *it*: a stable interface contract can sit at `1.0.0` /
`Production` while the model implementation beside it is still `0.1.0` /
`Development`. That independence is a reason to split in the first place, so do
not flatten it by copying the parent's numbers everywhere.

Two path rules govern child references:

- **Sibling child** → `..\Interfaces\ATAP.Utilities.Loader.Interfaces.csproj`
- **Anything outside the parent** → gains one extra `..` level, because the
  child sits one directory deeper than the original project did.
  `..\ATAP.Utilities.FileIO\...` becomes `..\..\ATAP.Utilities.FileIO\...`.

That second rule is the most common source of post-move build breakage. Every
relative path inherited from the original `.csproj` needs the extra level.

### Name children `<Parent>.<Role>.csproj` — never `<Parent>.csproj`

A child placed at `Model/ATAP.Utilities.Persistence.csproj` has the same *file
name* as its facade at `ATAP.Utilities.Persistence.csproj`. Visual Studio and
the solution format key on file name in several places, and the two collide.
The establishing commit had to go back and rename three such children after the
fact, then patch ten consumer `.csproj` files that had referenced them. Name the
child for its role from the start:

```text
Model/ATAP.Utilities.Persistence.Model.csproj        ✅
Model/ATAP.Utilities.Persistence.csproj              ❌ collides with the facade
```

### When a child is an executable

Console projects keep the entry point in `Model/` with `<OutputType>Exe</OutputType>`,
while the facade remains a `Library`. A library cannot link an executable's
output assembly, and the SDK reports this as `NETSDK1150`. Suppress the linkage
while keeping the build ordering:

```xml
<!-- ReferenceOutputAssembly=false prevents NETSDK1150:
     the facade doesn't try to link the Exe's output assembly -->
<ProjectReference Include="Model\ATAP.Console.PluginDemo.Model.csproj">
  <ReferenceOutputAssembly>false</ReferenceOutputAssembly>
</ProjectReference>
```

The reference still exists, so the executable is built when the facade is built.
Only the assembly-linking step is suppressed.

## Layering: which child may reference which

Children reference *downward* only. The dependency order established across the
Loader, Secrets, and ManimVideoGenerator conversions is:

```text
StringConstants  →  Enumerations  →  Interfaces  →  Model  →  Shim
```

A child must never reference the facade. The facade already references every
child, so a back-reference is a project cycle and MSBuild will refuse it. If a
child seems to need something from the facade, the thing it needs belongs in a
lower child instead — usually `StringConstants` or `Interfaces`.

`Shim/` deserves a note: shims adapt a third-party provider to the project's own
interfaces, and each provider gets its own nested project
(`Shim/Bitwarden/`, `Shim/Plugin/`) under a `Shim/` parent that is itself a
small facade. That nesting is recursive and the same rules apply at each level.

## Moving files with history intact

Use `git mv` for every relocation, including absorbed sibling projects. Git
records these as renames rather than as an unrelated delete plus add, which
keeps `git log --follow` and `git blame` working through the restructure — the
difference between a reviewable diff and an opaque one.

```powershell
git mv src/ATAP.Utilities.Loader.Interfaces src/ATAP.Utilities.Loader/Interfaces
git mv src/ATAP.Utilities.Loader/Loader.cs src/ATAP.Utilities.Loader/Model/Loader.cs
```

Never copy-then-delete. The reviewer of a large restructure relies on rename
detection to see that content is unchanged; without it every moved file reads as
newly written code that has to be re-reviewed line by line.

## Solution and consumer fixups

These steps are where a facade conversion is actually finished or actually
broken, and they are easy to skip because the facade itself already builds.

1. **Solution entries.** Every child needs its own `Project(...)` entry with a
   fresh GUID. The facade keeps its original GUID — changing it detaches build
   configuration and any tooling keyed to it. Group the family under a solution
   folder (`Project("{2150E333-...}")`) and map the children into it through the
   `NestedProjects` section so the solution view mirrors the directory layout.

2. **Consumer reference sweep.** Every `ProjectReference` in the repository that
   pointed at an absorbed sibling is now dangling. Search `src/` and `tests/`
   for the old paths and repoint them at the new nested location. Test projects
   are the ones most often forgotten — they frequently reference the
   `.Interfaces` sibling directly, which is exactly the kind of project that
   gets absorbed.

3. **Duplicate-name check.** Confirm no two `.csproj` files anywhere in the
   solution share a file name.

## Verify before claiming done

A facade conversion that builds in isolation can still have broken the
repository, so verify outward from the change:

```powershell
dotnet build src/<Parent>/<Parent>.csproj          # the facade and its children
dotnet build <Solution>.sln                        # every consumer
```

Then confirm the mechanical properties by inspection, because each one fails
silently rather than loudly:

- No `.cs` file compiles into more than one assembly — check that every facade
  has `EnableDefaultItems=false` and that any parent-level file it needs is
  listed in an explicit `Compile Include`.
- No `ProjectReference` in the repository resolves to a path that no longer
  exists.
- No two `.csproj` file names collide.
- No child references its own facade.
- The facade's path and file name are byte-identical to what they were before.

Report which of these you actually ran versus assumed, and write the build
output into the repository's `_generated/` folder as the evidence artifact.
