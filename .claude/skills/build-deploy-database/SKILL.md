# Build Deploy Database

Build an immutable ATAP Flyway database package, exercise it against a cloned
tier database, promote it through the reviewed BuildMaster pipeline, and prove
that the exact artifact and intended migrations reached every authorized tier.

Use this skill for ATAP database releases, BuildMaster database pipelines,
ProGet `database-*` feeds, Flyway migration promotion, and recovery of a
partially completed database stage. Do not use it for ad hoc SQL execution or
generic non-ATAP database deployment.

## Required input

- repository or database application name;
- intended package version;
- explicit migration boundary, including every intentional exclusion;
- highest authorized tier.

If the migration boundary is ambiguous, stop. Never infer that every untracked
or recently created SQL file belongs in a release.

## Non-negotiable gates

- Build once. Promote the same `.nupkg` bytes; never rebuild an existing
  version between tiers.
- BuildMaster owns publish, promotion, rehearsal, snapshot, and apply. Do not
  bypass it merely because a stage is difficult to repair.
- Treat each ProGet tier and its corresponding database as one stage gate.
  Publishing or promoting the artifact is not stage success: apply that exact
  artifact to the tier database, verify it, and only then complete the stage.
- Treat a queued deployment as pending, not successful.
- Rehearse against a backup/restore clone of the current target tier. An empty
  database is not representative when legacy migrations assume existing state.
- Take a verified, hashed full backup before changing Integration, QA, or
  Production.
- Never run `flyway repair` reflexively. First prove the exact mismatches,
  explain why migration text changed, take a backup, run repair with the exact
  immutable package, and record before/after history.
- A permanent SQL instance named `Experimental` is retired. The Experimental
  pipeline label must target an ephemeral `Exp<DeveloperName>` database
  instance. Never create or restore a permanent `Experimental` instance.
- Resolve credentials by host-suffixed Bitwarden secret name. Never print or
  persist secret values.
- Completion requires independent SQL history and ProGet artifact checks.

## 1. Select the source and migration boundary

Resolve one sprint worktree and read its repository instructions. Inventory:

- `Database/<Application>/version.json`;
- `Database/Flyway/SQL/V*.sql`;
- package manifest/configuration;
- current git status and commit;
- BuildMaster application, plan, pipeline, and tier variables.

Create an allowlist of included migrations and an explicit denylist. Inspect
untracked migrations separately. Record the target Flyway version.

For a deferred migration, exclude its exact filename at package construction
and assert that neither the `.nupkg` entries nor its manifest contain it.

## 2. Validate infrastructure before building

Confirm:

- BuildMaster and ProGet services and backing databases are healthy;
- the BuildMaster service identity can read the worktree;
- Git trusts only that exact worktree for the service identity;
- the service identity has the minimum SQL permissions needed by the reviewed
  pipeline;
- SQL Server and BuildMaster can both access the shared staging root;
- the Experimental stage resolves to an ephemeral developer instance;
- every tier connection secret resolves without exposing its value.

Use a dedicated staging root such as
`C:\ProgramData\ATAP\DatabasePackageStaging`. The BuildMaster service identity
and each target SQL Server service identity need the rights required for package
expansion and backup/restore.

Do not grant broad filesystem or SQL rights when an exact path, login, database,
or server role suffices. Record every provisioning change.

## 3. Build and inspect the immutable package

Prefer the current source-tree database commands over an older installed module
when the release uses newly changed command contracts:

- `New-DatabaseChangePackage`;
- `Expand-DatabaseChangePackage`;
- `Get-DatabasePackageManifest`;
- `Invoke-DatabasePackageRehearsal`;
- `Invoke-FlywayRehearsal`;
- `Invoke-Flyway`;
- `New-DatabasePreMigrationSnapshot`;
- ProGet database publish/promotion commands.

Build once, then record:

- package ID and version;
- package path, byte length, and SHA-256;
- source git SHA;
- manifest target version;
- migration and seed entries;
- destructive-change classification;
- exclusions.

Fail if an excluded migration appears anywhere in the archive or manifest.

## 4. Run local gates

Run focused package, manifest, Flyway, ProGet, BuildMaster plan, and API contract
tests. Preserve transcripts under a release-specific `_generated` directory.

Exercise the package against a cloned tier database:

1. connect with explicit local certificate trust where policy allows;
2. create a copy-only backup into the shared staging root;
3. restore it as a uniquely named rehearsal database;
4. run Flyway validate/migrate against the clone;
5. capture structured results without mixing native Flyway stdout into the
   PowerShell success object;
6. drop the rehearsal database in cleanup.

Do not promote after a failed rehearsal.

## 5. Create or verify the BuildMaster release

Use the reviewed database application and five logical stages:

1. Experimental — ephemeral `Exp<DeveloperName>` only;
2. Development;
3. Integration;
4. QA;
5. Production.

Capture application, release, build, deployment, target-execution, plan, and
pipeline identifiers. Verify application variables include the exact source
path, branch, package identity, ProGet endpoint/secret name, tier connection
secret names, and exclusion list.

When the UI cannot persist a pipeline, use the supported BuildMaster Native API
and record that fallback. Do not invent an unsupported REST contract.

## 6. Promote one stage at a time

For each stage:

1. start the deployment;
2. wait for both parent and target execution to reach terminal success;
3. inspect the execution log on failure;
4. confirm rehearsal success;
5. confirm ProGet publish/promotion;
6. apply the exact published/promoted artifact to that tier's database;
7. confirm snapshot for permanent tiers;
8. confirm the stage completion marker;
9. query `flyway_schema_history` independently.

Fail before publish or promotion when the current tier has no configured
connection-secret name. Do not allow an apply-bypass option to produce a
successful stage or completion marker.

Promotion must be retry-safe. A stage may fail after ProGet has already moved or
copied the package. If the exact package version is absent from the source feed
but present in the intended destination, treat promotion as already completed
and resume with the corresponding database apply and verification. If it is
absent from both, fail closed.

## 7. Handle checksum drift safely

If Flyway validation reports checksum mismatch:

1. stop before package promotion or database apply;
2. list every mismatched version and its database/local checksum;
3. compare checksums across lower tiers;
4. inspect git history for the changed migration files;
5. decide whether the old migration was improperly edited after application.

Prefer a new forward migration when the changed behavior must be applied to
existing databases. A repair only reconciles history; it does not execute the
new text.

Only when reconciliation is justified:

- create and hash a full backup;
- run `flyway repair` with the exact release package;
- verify only the expected history rows changed;
- rerun the complete BuildMaster stage.

Document the rationale and the limitation that repaired legacy logic did not
execute on databases where the migration had already run.

## 8. Prove completion

For every authorized tier database, including the approved
`Exp<DeveloperName>` target of the logical Experimental stage, query:

- latest successful Flyway version;
- count of intended release migrations;
- count of every excluded/deferred migration;
- failed history rows.

For ProGet:

- query the exact package/version in each expected database feed;
- download it from `database-stable`;
- compare its SHA-256 and byte length with the BuildMaster artifact;
- inspect its manifest and archive entries again.

Completion requires the stable hash to match, the intended history to be
present, exclusions to remain absent, and BuildMaster executions to be
terminal-success.

## 9. Record and checkpoint

Update:

- the repository database runbook and nearest `README.md`/`INDEX.md`;
- sprint task Markdown/HTML, accomplished log, and procedural details;
- a release evidence index with transcripts, hashes, execution IDs, backups,
  Flyway history, and known failures;
- this skill's operational reference when a new reusable failure mode is found.

Commit implementation, canonical skill, and planning documentation in their
own repositories with intentional scopes. Preserve unrelated user changes.

Read [operational-lessons.md](references/operational-lessons.md) when
diagnosing a failed or partially completed release.

## Final report

Report:

- worktree, application, package ID/version, source SHA, and package SHA-256;
- exact included and excluded migration boundary;
- BuildMaster release/build and per-stage execution results;
- database history result for every tier;
- ProGet feed and stable-download proof;
- backups and any Flyway repair;
- commits/checkpoint;
- anything still unresolved.
