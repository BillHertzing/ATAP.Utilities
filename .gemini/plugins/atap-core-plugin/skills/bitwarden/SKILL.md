# AI instructions for Bitwarden integration

Rules for accessing secrets from the organization's Bitwarden vault.

---

## PowerShell Access Pattern

Use the `Get-BitWardenSecret` cmdlet (from `ATAP.Utilities.BuildTooling.PowerShell`)
to retrieve secrets. Do NOT use the PowerShell Secrets Management vault extension —
it stores secrets in a parallel vault that is not visible in the Bitwarden UI.

```powershell
$secret = Get-BitWardenSecret -ItemName 'MySecretName'
```

---

## BW_SESSION Environment Variable

The Bitwarden CLI session token (`BW_SESSION`) is set at interactive login by
`LoginScript.ps1`. In agent-spawned shells, process-scope `$env:BW_SESSION` may
be empty. Read it from User scope:

```powershell
$bwSession = [System.Environment]::GetEnvironmentVariable('BW_SESSION', 'User')
```

---

## Automation Uses bws, Not bw (SC-0175)

`BW_SESSION` (personal-vault `bw` CLI session) is for personal-vault secrets
accessed by a real interactive user ONLY. All sprint start, sprint end, and
dry-run automation authenticates with `bws` (Bitwarden Secrets Manager CLI)
using a machine access token instead:

- Token resolution order: process-scope `$env:BWS_ACCESS_TOKEN`, then the
  DPAPI access-token file for the running account (`Get-BWSAccessToken`).
  Provision the token file with `Initialize-BWSAccessToken`.
- Per-sprint machine secrets (`dbConnectionString-*-<Dev|Exp>-<UserName>`)
  live in Bitwarden Secrets Manager (project `CI-Shared`), created by
  `New-SprintBitwardenSecrets` and deleted by `Remove-SprintBitwardenSecrets`.
- Sprint-automation reads go through
  `Get-SecretATAP -SecretName <name> -SecretStoreType 'BitwardenSecretsManager'`.
- Never make sprint automation depend on `bw login`, `bw unlock`, or
  `$env:BW_SESSION` — user-session-based automation hangs when the session is
  locked or stale.

## Adding New Secrets

Do NOT write a new secret value into source code, `appsettings.json`, or any committed
file. When a new secret is needed:

1. Stop and inform the user of the required secret and a suggested dotted-notation
   **SecretName** (e.g., `SEQ.Admin.API.Key`, `Windows.Remoting.Credential.UTAT01`).
   Do not suggest an environment-variable name.
2. The user adds the secret to Bitwarden under that SecretName.
3. Thereafter, resolve it by name at the point of use — never earlier, and never into
   a variable that outlives the authenticated call:
   ```powershell
   $value = Get-SecretATAP -SecretName 'SEQ.Admin.API.Key'
   ```

> **Do not export secrets as environment variables.** The older pattern — add to
> Bitwarden, export from `LoginScript.ps1` as a User-scope variable, then read with
> `[System.Environment]::GetEnvironmentVariable(...)` — was retired. The ProGet and
> BuildMaster API-key variables were deleted from every persistent User, Machine,
> service, and process-launch scope, and callers that still read them get nothing.
> `Get-SecretATAP` is the only resolution path.

If the secret authenticates a **placed service** (ProGet, BuildMaster), its SecretName
is host-suffixed as `<BaseName>.<placement-host>` (SC-0288); see
`ATAP.Utilities/SolutionDocumentation/SecretName-HostSuffix-Convention.md`. A
credential that authenticates the **caller** — notably the BWS access token — is the
same value on every host and is never suffixed.

## Bitwarden CLI vs. Secrets Management Extension

| Method                                | Vault visible in UI? | Use for        |
| ------------------------------------- | -------------------- | -------------- |
| `Get-BitWardenSecret` (Bitwarden CLI) | Yes                  | All secrets    |
| PowerShell Secrets Management vault   | No (separate vault)  | **Do not use** |

## Database Connection String Secrets (R-35)

Permanent-tier connection strings are Bitwarden Password Manager secure-note items
(store the connection string in the item's `connString` field). Per-sprint ephemeral
connection strings are Bitwarden Secrets Manager secrets (the secret value IS the
connection string; see SC-0175 above). Never commit connection strings, SQL
passwords, API keys, or vault exports.

### Naming Patterns

Permanent tier instances use no username suffix:

```text
dbConnectionString-<Database>-<Host>-<Production|QA|Integration>
```

Per-sprint ephemeral instances include the developer username:

```text
dbConnectionString-<Database>-<Host>-<Dev|Exp>-<UserName>
```

Use the short tier tokens `Dev` and `Exp` for ephemeral sprint instances. Do not use
`Development` or `Experimental` in the Bitwarden item name unless a specific legacy
call site requires it.

### Permanent Tier Secrets

The canonical permanent databases are `AceCommander` and `ATAPUtilities`. For the
current workstation host `utat022`, the permanent tier matrix is:

| Database | Tier | Bitwarden item |
| --- | --- | --- |
| `AceCommander` | `Integration` | `dbConnectionString-AceCommander-utat022-Integration` |
| `AceCommander` | `QA` | `dbConnectionString-AceCommander-utat022-QA` |
| `AceCommander` | `Production` | `dbConnectionString-AceCommander-utat022-Production` |
| `ATAPUtilities` | `Integration` | `dbConnectionString-ATAPUtilities-utat022-Integration` |
| `ATAPUtilities` | `QA` | `dbConnectionString-ATAPUtilities-utat022-QA` |
| `ATAPUtilities` | `Production` | `dbConnectionString-ATAPUtilities-utat022-Production` |

Permanent connection strings use SQL Server instances named for the tier:

```text
Server=<Host>\<Tier>;Database=<Database>;Integrated Security=True;MultipleActiveResultSets=True;TrustServerCertificate=True;
```

### Ephemeral Sprint Secrets

Sprint start creates per-developer `Dev<UserName>` and `Exp<UserName>` SQL Server
instances. The default host list is the workstation name and `localhost`, and the
canonical databases are `master`, `ATAPUtilities`, and `AceCommander`.

For user `whertzing`, the `master` database secrets for the two ephemeral sprint
instances are:

| Host | Tier | Bitwarden item |
| --- | --- | --- |
| `utat022` | `Dev` | `dbConnectionString-master-utat022-Dev-whertzing` |
| `utat022` | `Exp` | `dbConnectionString-master-utat022-Exp-whertzing` |
| `localhost` | `Dev` | `dbConnectionString-master-localhost-Dev-whertzing` |
| `localhost` | `Exp` | `dbConnectionString-master-localhost-Exp-whertzing` |

Use the same host/tier/user pattern for `AceCommander` and `ATAPUtilities` sprint
secrets. Example: `dbConnectionString-AceCommander-localhost-Dev-whertzing`.

### Master Database Coverage

The `master` database needs a connection string for every SQL Server instance an agent
may create, migrate, inspect, or tear down:

| Instance class | Instance names | Required `master` secret pattern |
| --- | --- | --- |
| Permanent | `Integration`, `QA`, `Production` | `dbConnectionString-master-<Host>-<Tier>` |
| Ephemeral | `Dev<UserName>`, `Exp<UserName>` | `dbConnectionString-master-<Host>-<Dev|Exp>-<UserName>` |

When writing tooling that creates or removes databases, resolve the `master` connection
string first. Do not derive it by editing an application database connection string unless
there is no Bitwarden item and the user explicitly approves that fallback.

End of instructions.
