## What is being built, and why this shape

`/implement-task` is a top-level orchestrator that takes a task number or range,
implements it by delegating to worker subagents, and closes the loop by updating the
board, the nearest index/readme, the evidence tree, then committing and checkpointing.

The design constraint that drives everything: **an orchestrator holds a minimal tool
surface and does no file mutation itself.** It reads, dispatches, and integrates. Every
write is attributable to a named subagent. This is not stylistic — it is what makes the
blast radius of an agent bounded and auditable.

Four tiers, each with a gated tool surface:

| Tier | Members | Tool surface |
| --- | --- | --- |
| 1 orchestrator | `implement-task` | read, edit, agent, terminal — nothing else |
| 2 worker | `JuniorDevCoder-JL` / `-JM` / `-SH` | adds search, todo; `agent` restricted to `gather-content-summary` |
| 3 MCP isolation | `mcp-dab-contentsummary` | file read/write/edit + exactly one server's MCP tools; no terminal, no agent |
| 4 support | `gather-content-summary`, `board-reconcile`, `index-readme`, `evidence-recorder` | minimum for one responsibility |

No orchestrator and no worker ever holds an MCP tool directly. The blast radius of a
misbehaving MCP server is one subagent's declared surface.

## Decisions already made — do not relitigate

1. **`JuniorDevCoder` ships as three rendered variants**, not one agent with a runtime
   effort parameter. The harness sets model in frontmatter and accepts a per-call model
   override, but **reasoning effort is not a per-invocation parameter**. Effort is
   therefore baked into the variant: `-JL` low, `-JM` medium, `-SH` high, over one shared
   body. Model stays a per-call override.
2. **Dispatch requires an explicit HITL approval gate.** The orchestrator presents a batch
   plan and stops. Unattended dispatch was considered, approved, then rescinded on
   2026-08-04; it is deferred until the gate has proven the selection logic. Do not build
   an unattended path "for later".
3. **ContentSummary retrieval is stubbed.** See the stub contract below.
4. **`SwarmDispatchOrchestrator` is out of scope.** `/implement-task` dispatches directly.
   The approval gate and claim ledger were pulled forward into `/implement-task` because
   they are needed the moment anything dispatches, not only for batches.
5. **Shared-manifest writes are coordinator-only.** See the disjointness rule below.

## The stub contract

`gather-content-summary` and `mcp-dab-contentsummary` are built now with **real
interfaces and a live call path, but absent retrieval**, because the ContentSummary
schema is not final (blocked on `RDB-190`, `RDB-260`, and Stream D).

A stub here means:

- The agent exists, is registered, renders, and is callable with its full documented
  argument list — `Tags`, `Depth` default 3, `Width` default 2, `Instance` default
  `production` (any registered SQL Server instance).
- It returns a **typed empty result carrying an explicit `NotImplemented` marker** naming
  the blocking dependency. Never an error, never silence, **never fabricated content**.
- Every caller handles that marker as a first-class case and records it as a coverage
  finding, so **a stubbed run stays visibly distinguishable from a real run that found
  nothing**. This is the property that matters: a worker must never look like it had
  context when it did not.
- Nothing downstream branches on ContentSummary entity names, column names,
  `Depth`/`Width` traversal semantics, or return shape — all four are unsettled.
- Un-stubbing later changes only the retrieval body, not the interface and not any caller.

For `mcp-dab-contentsummary`, the entity allow-list must be a **named placeholder that
fails closed**. An empty allow-list that permits everything is the failure mode to avoid —
it would make the stub broader than the real agent it stands in for.

Live DAB traffic additionally requires MCP launch pinning (Task 14.113 / SC-0303) — not
blocking while stubbed, blocking the moment real traffic is enabled.

## The disjointness rule, and why the waves look like this

Every agent-authoring unit naturally wants to touch the same three shared manifests:
`.ai/config/common/toolsets.json`, `.ai/manifests/toolsets-map.json`, and
`.ai/manifests/instruction-map.json`. If workers wrote them directly, no two agent units
could run in parallel and the disjoint-write-scope rule would be violated on every
dispatch.

**Resolution, matching the existing policy that the coordinator alone integrates shared
artifacts:** a worker authors *only* its own agent file. All shared-manifest registration
and every `Render-AIAdapters` run is a coordinator-owned unit (Task 14.199, profile
`C-H`). Workers never touch a manifest, never render, and never commit.

This produces the wave shape: fan out to author files → coordinator integrates → fan out
again. Peak parallelism is 10 disjoint single-file units. Tasks 14.133.a/b/c are
deliberately serial because all three edit the same shared body file.

## Failure modes to design against

- **Rendered-but-invisible.** A target can pass drift checks with a green content hash
  while the consuming tool sees nothing — this is exactly what Task 14.60.a found, where
  Codex skill renders landed in `.agents/`, a directory Codex never reads. **Prove
  availability by a fresh session listing each agent by name, never by a manifest hash.**
  Task 14.199.b exists solely for this.
- **Rubber-stamp approval.** A gate that presents an unreviewable plan — too long, too
  vague about writable scopes — produces reflexive approvals and is no better than no
  gate. The plan must be auditable in one pass.
- **Silent context loss.** A worker that treats a stub response as "nothing found" and
  proceeds quietly. The handoff must show the derived tags, the call, and the coverage
  finding.
- **Lost board updates.** `Tasks.Sprint0014.md` and its HTML are edited concurrently by
  other sessions. `board-reconcile` re-reads before writing and never blind-overwrites.
- **Bootstrapping.** `JuniorDevCoder` does not exist until Task 14.131 lands, so early
  units are dispatched manually under `.ai/policy/agent-swarm-dispatch.md`. From Task
  14.199 onward the stream can dispatch itself; Task 14.160 rehearses exactly that.
