# AI instructions for building the `/implement-task` agent system

Implementation brief for a senior developer agent building or modifying the
`/implement-task` orchestrator, the `JuniorDevCoder` variants, the MCP isolation
subagents, or the Tier-4 support subagents.

This file explains **how the agent system is constructed and why it has this shape**. It
is not the runtime workflow — `/implement-task` invokes the `implement-task` skill, which
routes to the orchestrator contract in `.ai/agents/implement-task.agent.md`. That contract
owns the sequence; nothing here restates it.

Authority chain: the sprint's agent design plan (design decisions and HITL decisions of
record) → the active sprint board entry for the work → `.ai/policy/agent-swarm-dispatch.md`
(profiles, claim ledger, worker prompt contract). Nothing here weakens an acceptance
criterion in those documents. The construction history of the original build — task

`_Planning/InformationForTheFuture/StreamL-ImplementTask-Build-History.md`.

## What is being built, and why this shape

`/implement-task` is a top-level orchestrator that takes a task number or range,
implements it by delegating to worker subagents, and closes the loop by updating the
board, the nearest index/readme, the evidence tree, then committing and checkpointing.

The design constraint that drives everything: **an orchestrator holds a minimal tool
surface and does no file mutation itself.** It reads, dispatches, and integrates. Every
write is attributable to a named subagent. This is not stylistic — it is what makes the
blast radius of an agent bounded and auditable.

Four tiers, each with a gated tool surface:

| Tier | Members | Tool surface |
| --- | --- | --- |
| 1 orchestrator | `implement-task` | read, edit, agent, terminal — nothing else |
| 2 worker | `junior-dev-coder-jl` / `-jm` / `-sh` | adds search, todo; `agent` restricted to `gather-content-summary` |
| 3 MCP isolation | `mcp-dab-contentsummary` | separate MCP path; no role in REST retrieval |
| 4 support | `gather-content-summary`, `board-reconcile`, `index-readme`, `evidence-recorder` | minimum for one responsibility |

No orchestrator and no worker ever holds an MCP tool directly. The blast radius of a
misbehaving MCP server is one subagent's declared surface. The `gather-content-summary`
compatibility wrapper uses the reviewed PowerShell REST client and does not enter this MCP path.

## Decisions already made — do not relitigate

1. **`JuniorDevCoder` ships as three rendered variants**, not one agent with a runtime
   effort parameter. The harness sets model in frontmatter and accepts a per-call model
   override, but **reasoning effort is not a per-invocation parameter**. Effort is
   therefore baked into the variant: `-jl` low, `-jm` medium, `-sh` high, over one shared
   body. Model stays a per-call override.
2. **Dispatch goes through an HITL approval gate that waits, then auto-continues.** The
   orchestrator presents a batch plan and the gate waits for an explicit **approve**,
   **reject**, or **approve-subset** response. Absent any response it waits five minutes
   by default — configurable per run — and then auto-continues, dispatching the
   dispatchable set unattended.

   Auto-continue is a decision path *through* the gate, not a way around it. **Every
   refusal the gate makes on an explicit approval it makes identically on timeout**: a
   plan in which two units contend for the same write scope, a plan over the one-pass
   review budget, a plan with nothing dispatchable, and an approval that cannot be
   recorded to the coordination ledger all refuse and dispatch nothing. Build the timeout
   as a decision the gate reaches, never as a branch that skips its checks — an unsafe
   plan does not become safe because nobody objected to it in five minutes.

   **History of the unattended-dispatch decision — read both entries, in order.**

   *2026-08-04 — superseded, retained as history.* The rule in force was: unattended
   dispatch was considered, approved, then rescinded; it was deferred until the gate had
   proven the selection logic, and the standing instruction to builders was "do not build
   an unattended path 'for later'."

   *2026-08-21 — current, Task 15.73.* The operator supersedes that rescission. The gate
   is present-and-wait-with-timeout, and the timeout auto-continue path above **is**
   sanctioned unattended dispatch. The 2026-08-04 entry is kept as dated history rather
   than deleted, so a builder who meets the old rule in a rendered copy, an older branch,
   or an agent's own memory can see that it was superseded, on what date, and by which
   task — instead of concluding the shipped gate violates a rule still in force and
   reverting it.
3. **ContentSummary retrieval is live through the PowerShell REST client.** See the
   retrieval contract below.
4. **A separate swarm-dispatch orchestrator is out of scope.** `/implement-task` dispatches
   directly. The approval gate — including the wait and the timeout auto-continue path of
   decision #2 — and the claim ledger live inside `/implement-task` because they are
   needed the moment anything dispatches, not only for batches.
5. **Shared-manifest writes are coordinator-only.** See the disjointness rule below.

## The ContentSummary retrieval contract

`gather-content-summary` preserves its callable arguments — `Tags`, `Depth` default 3,
`Width` default 2, and `Instance` default `production` — while invoking the reviewed
`Get-ContentSummary` PowerShell client. That client alone resolves configuration, calls the
AceOutpost loopback HTTPS REST route, validates the stable envelope, and writes the mandatory
gather-call record.

Callers distinguish four outcomes without adapting the interface:

- populated `status: "ok"` uses only the returned items;
- `status: "ok"` with `items: []` is an explicit real empty result, including the
  fail-closed authorized-empty case;
- transport, configuration, certificate, response-validation, and other retrieval failures
  remain failures and are never converted to empty success;
- recording failure makes the invocation fail and cannot be reported as recorded success.

Direct source reads remain the documented worker fallback for an empty result or retrieval
failure when the declared repository scope permits them. Every fact from that fallback is
attributed to the direct read. Neither the wrapper nor a caller fabricates paths, summaries,
items, or representative results.

The separate `mcp-dab-contentsummary` path remains stubbed. Its entity allow-list must be a
**named placeholder that fails closed**. An empty allow-list that permits everything is the failure mode to avoid —
it would make the stub broader than the real agent it stands in for.

Live DAB traffic additionally requires MCP launch pinning — not blocking while stubbed,
blocking the moment real traffic is enabled.

## The disjointness rule

Every agent-authoring unit naturally wants to touch the same three shared manifests:
`.ai/config/common/toolsets.json`, `.ai/manifests/toolsets-map.json`, and
`.ai/manifests/instruction-map.json`. If workers wrote them directly, no two agent units
could run in parallel and the disjoint-write-scope rule would be violated on every
dispatch.

**Resolution, matching the existing policy that the coordinator alone integrates shared
artifacts:** a worker authors *only* its own agent file. All shared-manifest registration
and every `Render-AIAdapters` run is a coordinator-owned unit at profile `C-H`. Workers
never touch a manifest, never render, and never commit.

This produces the wave shape: fan out to author files → coordinator integrates → fan out
again. Units that edit a shared body file are serialized against each other rather than
fanned out.

## Build order

1. **The toolset gate comes first — it blocks everything.** Define the four named toolset
   profiles and extend `Test-AIAdapterToolsetGate.ps1` to fail on any agent declaring a
   tool outside its profile or enumerating raw tool ids. Without an enforcing gate,
   "minimal tool surface" is prose, not a property.
2. **Contracts before agents** — the worker input contract, into
   `.ai/policy/agent-swarm-dispatch.md`, and the handoff schema plus its validator. The
   handoff schema must make the verified/asserted split **structural**, so the two cannot
   be blended in one field.
3. **Author agent files in parallel.** One file per unit.
4. **Coordinator integration** — register every agent in `instruction-map.json`, render,
   prove zero drift.
5. **Orchestrator internals** — board resolution, variant selection, approval gate and
   claim ledger, closeout chain, continue-after-crash.
6. **Context step**, serialized against the shared body file it edits.
7. **Rehearsal**, with the expected outcome pre-recorded before dispatch so the run cannot
   be scored after the fact.

## Failure modes to design against

- **Rendered-but-invisible.** A target can pass drift checks with a green content hash
  while the consuming tool sees nothing — because the path is wrong, the format is
  silently rejected, or the surface is rendered at project scope when the caller runs
  somewhere else. **Prove availability by a fresh session listing each agent and skill by
  name, never by a manifest hash.** See
  `_Planning/InformationForTheFuture/AIAdapter-agent-surface-consumption-findings.md`,
  which records this failure recurring across four sprints and three harnesses.
- **Omitting a `tools:` key is a privilege grant, not a neutral default.** A harness that
  sees no tool declaration grants its full set. Never drop the key to work around an
  untranslatable tool name.
- **Rubber-stamp approval.** A gate that presents an unreviewable plan — too long, too
  vague about writable scopes — produces reflexive approvals and is no better than no
  gate. The plan must be auditable in one pass.
- **Silent context loss.** A worker that treats a stub response as "nothing found" and
  proceeds quietly. The handoff must show the derived tags, the call, and the coverage
  finding.
- **Lost board updates.** The sprint board and its HTML companions are edited concurrently
  by other sessions. `board-reconcile` re-reads before writing and never blind-overwrites.
- **Bootstrapping.** Until the worker variants exist, units are dispatched manually under
  `.ai/policy/agent-swarm-dispatch.md`. Once they are registered and proven available, the
  stream can dispatch itself.
