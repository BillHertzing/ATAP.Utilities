# Git Commit Skill

You are performing a structured git commit. The entire flow is implemented as
**a single `pwsh -File` invocation** of `Invoke-GitCommit.ps1`. That script
handles context gathering, sensitive-file detection, scoped staging, message
composition, commit, and confirmation. The skill itself does **not** run inline
`pwsh -Command` calls — those require per-invocation approval and break the
flow.

The `pwsh -File:*` permission is already granted in the project allow-list, so
invoking the script does not prompt.

> ⚠ **Surgical by design — commit only the files you name.** This skill is used
> to commit the specific files an agent worked on during the current
> conversation, **not** to sweep every dirty file in the working tree. Always
> pass the explicit list of paths you intend to commit. The script never runs
> `git add -A`; anything you do not list is left unstaged and untouched.

## Step 1 — Decide which files to commit

Before invoking the script, build the explicit list of paths you changed in this
conversation. That list is what the commit is scoped to — every dirty path you
do **not** list stays unstaged. Do not include files you did not work on, even
if `git status` shows them as dirty.

```powershell
$ghRoot  = 'C:\Dropbox\whertzing\GitHub'
$relPath = 'src\ATAP.Utilities.BuildTooling.GitWorktree.PowerShell\public\Invoke-GitCommit.ps1'

$candidate = Get-ChildItem $ghRoot -Directory -ErrorAction SilentlyContinue |
    Where-Object { $_.Name -match '^ATAP\.Utilities-wt-\d+-[Ss]print-\d{4}-' } |
    Sort-Object Name -Descending |
    Select-Object -First 1

$scriptPath = if ($candidate) { Join-Path $candidate.FullName $relPath } else { $null }

    $scriptPath = Join-Path $ghRoot "ATAP.Utilities\$relPath"

Import-Module PSFramework -ErrorAction SilentlyContinue
. $scriptPath
Invoke-GitCommit -Groups @(
  @{ Paths   = @(
       'src/MyProject/Thing.cs',
       'src/MyProject/Thing.Tests.cs'
     )
     Message = 'feat(thing): add Thing with coverage' }
)
```

The function will:

1. Print `git status`, recent log, and a diff summary so you can review.
2. Detect and block sensitive files (`.env`, `*.secret`, `*.key`,
   `node_modules/`, `bin/`, `obj/`).
3. Stage **only the paths you supplied** (`git add -- <paths>`) — it never runs
   `git add -A` and never sweeps unrelated dirty files.
4. Use the Conventional Commits message you supplied for each scope.
5. Commit, print the resulting hash, and report how many dirty paths it left
   unstaged because they were not listed.

`Paths` accepts exact files or globs (for example `'src/MyProject/**'`). Only
changed paths that match an entry are staged and committed.

### Committing several task scopes in one call

Supply more than one group to create separate task-scoped commits in a single
invocation. Each group stages only its matched paths and gets its own message:

```powershell
Invoke-GitCommit -Groups @(
  @{ Paths = @('src/App/**'); Message = 'feat(app): update app flow' },
  @{ Paths = @('docs/**');    Message = 'docs(runbook): update app notes' }
)
```

### Single cohesive change

When the files you touched form one cohesive change, you may pass a single
message instead of a group. This still commits only your changes when the tree
holds nothing else; if the dirty tree spans more than one detected scope the
function refuses to collapse them unless you add `-ForceSingleCommit`:

```powershell
Invoke-GitCommit -Message "feat(auth): add OAuth2 token refresh"
```

> Running `Invoke-GitCommit` with **no arguments** is interactive (it prompts
> per scope via `Read-Host`) and is meant for a human at the console. From an
> agent, always pass `-Groups` (preferred) or `-Message` so the run is
> non-interactive and explicitly scoped.

## Step 5 — Checkpoint After a Successful Commit

> ⚠ **Run `/checkpoint` immediately after a successful commit.** A commit records
> code in git, but it does NOT update the sprint `_Planning` worktree. The
> conversation archive, memory snapshot, and session roster only advance when
> `/checkpoint` runs, so SprintEnd can verify checkpoint coverage by worktree
> name. Skipping it leaves the planning worktree out of sync with the committed
> work.

Once the commit(s) report success:

1. Run `/checkpoint` (alias `/cp`) from the same repository root you just
   committed in. It archives the conversation, copies memory files, and appends a
   roster entry to the sprint `_Planning` worktree.
2. If you committed in more than one repository, run `/checkpoint` once per repo
   root (change directory between runs).
3. This satisfies the checkpoint-cadence rule (R-30): checkpoint at completed task
   boundaries, before risky context switches or broad refactors, and always before
   closing the session.

This step is a reminder, not a blocker — the commit is already durable. But do
not end a work session on a commit without a following `/checkpoint`.

## Conventional Commits Reference

```text
<type>(<scope>): <summary>

[optional body — wrap at 72 chars]

[optional footer — BREAKING CHANGE: ..., Closes #42]
```

| Type       | When to use                             |
| ---------- | --------------------------------------- |
| `feat`     | New feature or capability               |
| `fix`      | Bug fix                                 |
| `refactor` | Code restructured, no behavior change   |
| `docs`     | Documentation only                      |
| `test`     | Adding or updating tests                |
| `chore`    | Build scripts, deps, tooling, config    |
| `style`    | Formatting, whitespace, no logic change |
| `perf`     | Performance improvement                 |
| `ci`       | CI/CD pipeline changes                  |

Summary line rules: imperative mood, max 72 chars, no trailing period,
lowercase after the colon.
