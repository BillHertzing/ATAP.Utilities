# Issue to Worktree

Turn a bounded unit of work into a GitHub issue, implementation plan, feature
branch, sibling worktree, initialized repository context, and concrete AI
adapter files.

## 1. Establish the work item

Use details already present in the conversation. Ask one focused question only
when the title, desired outcome, or acceptance criteria cannot be inferred
safely.

Prepare:

- a concise issue title;
- the problem or requested capability;
- constraints and relevant evidence;
- an implementation plan;
- tests and validation;
- a definition-of-done checklist.

## 2. Inspect the repository

Run from the repository root:

```powershell
$repoRoot = (& git rev-parse --show-toplevel).Trim()
if (-not $repoRoot) {
  throw 'The current directory is not inside a Git repository.'
}
Set-Location -LiteralPath $repoRoot

git status --short --branch
git remote -v
git branch --show-current
```

Do not modify or discard existing changes. The issue worktree is created from
the fetched remote default branch, so the current worktree does not need to be
clean.

## 3. Create the GitHub issue

Use the caller's connected GitHub issue tool when available. Otherwise use
`gh issue create`.

Use this body:

```markdown
## Context

<problem, desired outcome, constraints, and evidence>

## Implementation plan

1. <step>
2. <step>

## Validation

- <test or verification>

## Definition of done

- [ ] <acceptance criterion>
```

Capture the issue number and URL.

## 4. Create the branch and sibling worktree

Fetch the remote default branch without pulling or changing the current branch:

```powershell
git fetch origin main
```

Build a short kebab-case title and create a sibling worktree:

```powershell
$issueNumber = '<issue-number>'
$issueTitle = '<issue-title>'
$repoName = Split-Path -Path $repoRoot -Leaf
$repoParent = Split-Path -Path $repoRoot -Parent
$shortTitle = (($issueTitle -split '\s+' | Select-Object -First 6) -join ' ').ToLowerInvariant()
$shortTitle = ($shortTitle -replace '[^a-z0-9]+', '-').Trim('-')

$branchName = "$issueNumber-$shortTitle"
$worktreeName = "$repoName-wt-$issueNumber-$shortTitle"
$worktreePath = Join-Path -Path $repoParent -ChildPath $worktreeName

if (Test-Path -LiteralPath $worktreePath) {
  throw "Worktree path already exists: $worktreePath"
}
if (& git show-ref --verify --quiet "refs/heads/$branchName") {
  throw "Local branch already exists: $branchName"
}

git worktree add -b $branchName $worktreePath origin/main
```

Do not create ordinary sprint work on `main` or in a stable worktree.

## 5. Apply SharedVSCode repository context

Do not hand-edit `.git/config`, `.gitattributes`, `.gitconfig.shared`,
`core.hooksPath`, or workspace `templateRef` values.

Resolve the SharedVSCode source:

- normal issue worktree: use the stable `SharedVSCode` worktree;
- work explicitly validating SharedVSCode sprint changes: use the named
  SharedVSCode sprint worktree from current task context.

Do not ask for a path that can be discovered from the workspace, repository
siblings, or active task instructions.

Load the repository's SharedVSCode context functions and apply them to every
`.code-workspace` file in the new worktree. Prefer
`Initialize-DownstreamSprintFromSharedVSCode` for sprint validation and
`Set-DownstreamSharedVSCodeContext` for normal issue work.

Verify the resolved template reference, hooks path, and commit template with
`Get-SharedVSCodeContext`.

Do not create these roots as junctions. Do not call a junction replication
workflow that includes any of these roots.

## 8. Open the worktree

Opening or replacing a VS Code window is an external UI action. Ask for
confirmation immediately before doing it.

Prefer the worktree's `.code-workspace` file:

```powershell
$workspaceFile = Get-ChildItem -LiteralPath $worktreePath -Filter '*.code-workspace' |
  Select-Object -First 1

if ($workspaceFile) {
  code --reuse-window $workspaceFile.FullName
} else {
  code --reuse-window $worktreePath
}
```

## Safety rules

- Use PowerShell 7 syntax only.
- Preserve unrelated worktree changes.
- Never delete or retarget a junction automatically.
- Never write generated evidence outside the repository's `_generated/` folder.
- Use current repository lifecycle functions rather than reproducing their
  internals in the skill.
- If a remote operation, issue creation, or UI action requires authorization,
  request it at the point of use.
