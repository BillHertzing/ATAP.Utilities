# AI instructions for PowerShell files

This file is a set of instructions for AI to follow when generating or modifying PowerShell (.ps1) files in this repository.

## Agent Shell Command Requirements

This repository runs on **Windows** inside **Visual Studio Code**. When an AI agent needs to run terminal or shell commands (not just generate PowerShell source files), those commands MUST be PowerShell 7.x (pwsh) commands:

- Never use bash, sh, zsh, or POSIX shell commands in terminal invocations.
- Never use bash utilities: `ls`, `grep`, `sed`, `awk`, `export`, `&&`, `\` for line continuation.
- Always use PowerShell equivalents: `Get-ChildItem`, `Select-String`, `Get-Content`, `$env:VAR = 'value'`, `;` for chaining, `` ` `` for line continuation.

When running Pester from terminal commands, always allow PowerShell profiles (machine and user). Do not use -NoProfile. Prefer:
pwsh -Command "Invoke-Pester -Path '<path>' -Output Detailed"

## Module structure and creation

Each PowerShell project in this repository should have the following folders:

- Documentation
- public
- private
- tests
- lib _(optional — C# type-definition files only; see "Type Definition Files" below)_

The root of the Powershell project should have a .psd1 file that defines the module, and a .psm1 file that serves as the entry point for the module. The .psm1 file should import all public functions from the public folder, and all private functions from the private folder. The .psd1 file should specify the module's metadata, including its name, version, author, and dependencies.

### module.build.ps1

This file contains a standard build script that should be used for building all PowerShell modules in this repository. This creates the final .psm1 and .psd1 files. `Invoke-build` will walk up the folder stricture until it finds the module.build.ps1 file, so it can be run from any subfolder of the module.

The current set of repositories places the 'source of truth' for module.build.ps1 at the root of the ATAP.Utilities worktree (stable or sprint as appropriate). Future architecture may move the 'source of truth' location to the SharedVSCode worktree, with a symbolic link at the root of the ATAP.Utilities worktree pointing to the source of truth in SharedVSCode.

### Alias placement in packaged modules

Define public aliases with the function-level `[Alias('Name')]` attribute on the
function that implements the behavior. Do not define exported aliases with
`Set-Alias` or `Export-ModuleMember -Alias` in a source `.psm1` or a `public`/`private`
`.ps1` file: `Build-PSModulePsm1` rebuilds the shipped module from the function
folders and can discard those module-level declarations. Keep `AliasesToExport` in
the module manifest aligned with `[Alias()]` attributes, and add a contract test that
each manifest alias resolves after importing the built module.

## Type Definition Files (C# Add-Type)

Some modules ship C# types compiled at import time via `Add-Type` (e.g. the `PS_LSA`
LSA wrapper in `ATAP.Utilities.PowerShell`). These files define no functions, so they
must NOT live in `public/` or `private/`:

- `public/*.ps1` basenames become `FunctionsToExport` when the manifest is generated —
  a non-function file there produces a phantom export and breaks the published module.
- The "module .ps1 files define only functions" rule forbids top-level executable code
  in function directories.

Canonical pattern:

1. Place the type definition in `lib/<Name>.types.ps1` under the module root.
   `lib/` is dot-sourced by the module `.psm1` at import time and is included in the
   built (concatenated) `.psm1` by `Build-PSModulePsm1`, but is never scanned for
   exports.
2. The file contains exactly one guarded `Add-Type` statement and nothing else:

   ```powershell
   if (-not ('My.Namespace.SomeType' -as [type])) {
     Add-Type @'
   // C# source here
   '@
   }
   ```

   The guard makes the file idempotent: safe on every `Import-Module -Force`, safe to
   dot-source directly when running from source, and a no-op when another copy of the
   module already loaded the type into the appdomain.

3. Public functions MAY reference the type in `param()` blocks (e.g.
   `[PS_LSA.Rights[]] $Right`): PowerShell resolves parameter type constraints at first
   invocation, after import has loaded the type — file ordering inside the built psm1
   does not matter.
4. A function that can run standalone from source should verify the type in its BEGIN
   block (`'My.Namespace.SomeType' -as [type]`) and dot-source the `lib` file by
   relative path as a fallback, throwing a clear message if it cannot be found.
5. When enumerating `lib`, `public`, and `private` files in a `.psm1`, wrap the whole
   assignment in `@( )` (`$files = @(if (...) { Get-ChildItem ... })`) — assignment from
   an `if`/pipeline expression unwraps a one-element result to a scalar and breaks
   array concatenation.

## Coding Rules for PowerShell

- **Function Shape**:
  - unless especially called out in the comments at the top of the file, every file should contain an eponymous function declaration. all functions should be in the form of a cmdlet with a BEGIN block, a PROCESS block, and an END block, even if the function only needs to use one of those blocks. This is to ensure consistency across all functions and to make it easier to add functionality in the future if needed.

- **General Formatting**:
  - Use the .editorconfig file in the root of the repository for formatting rules.
  - Use spaces around operators and after commas.
  - Use single quotes for strings unless interpolation is required.
  - Avoid trailing whitespace at the end of lines.
- **Function Naming**:
  - Use PascalCase for public functions and parameters.
  - Use camelCase for private/internal functions and variables.
- **Cmdlet Design**:
  - Include `[CmdletBinding()]` and `param()` blocks with proper validation attributes.
  - Ensure all cmdlets support `-WhatIf` and `-Confirm` parameters.
  - The BEGIN{} block should start with the variables `$fn` and `$mn` and are populated with the Function Name (eponymous to the file name) and the Module Name. Use the actual function (file) name, and the module name. These variables are used in all logging statements.

  - if you find parameter validation being done in the process block, hoist it to the BEGIN block.

- **Comment-Based Help**:
  - Add or update `.SYNOPSIS`, `.DESCRIPTION`, `.PARAMETER`, `.OUTPUTS`, `.EXAMPLE`, `.NOTES`, and `.LINK` sections for all public functions.

- \*Loading helper functions
  - The following block of code should appear in the Begin block just after logging the starting of the function

```Powershell
  # Load helper functions
  # None of this is needed once the modules are built and installed into the PSModulePath, but while we are still running from source code, we need to dot source the helper functions that are not yet in a module.     @{FunctionName = 'Get-RepositoryRoot'; ModuleName = 'ATAP.Utilities.BuildTooling.Common.PowerShell'},

    Write-PSFMessage -FunctionName $fn -ModuleName $mn -Level Error -Message $errorMessage
```

- **Function Returns**:
  - All functions should return a string, a filehandle, a dotnet type defined in a loaded .DLL, or a PSCustomObject.
- **Error Handling**:
  - Wrap all potentially failing operations in a `try/catch/finally` block.
  - All calls to `Invoke-RestMethod` should be wrapped in a try/catch/finally block
  - All calls to `Invoke-WebRequest` should be wrapped in a try/catch/finally block.
  - All calls to `Invoke-Expression` should be wrapped in a try/catch/finally block.
  - All calls to `Invoke-Command` should be wrapped in a try/catch/finally block.
  - Log errors using `Write-PSFMessage` with `-Level Error`.
- **Logging**:
  - Use `Write-PSFMessage` for logging:
    - `-Level Debug` for trace messages.
    - `-Level Verbose` for lifecycle messages.
    - `-Level Important` for notable operational messages.
    - `-Level Error` for failures.
    - use `Write-PSFMessage` for logging, never `Write-Host`, `Write-Verbose`, `Write-Debug` or `Write-Output`.
    - use `-Level Debug` for trace messages, `-Level Verbose` for lifecycle messages, `-Level Important` for notable operational messages, and `-Level Error` for failures.
    - Never use -Level Info with `Write-PSFMessage`.
    - Every `Write-PSFMessage` inside a function should include the first two parameters `-FunctionName $fn -ModuleName $mn`
    - All calls to `Invoke-RestMethod`, `Invoke-WebRequest`, `Invoke-Expression`, `Invoke-Command` should have a log message just before and just after the line that calls the respective cmdlet. These log messages should have `-Level Debug`, and `-Tag 'RestCall' or 'WebRequestCall' or 'InvokeExpressionCall' or 'InvokeCommandCall'`. The message for the log before the call is "Calling `URLOfEndpoint` or `command`. The message for the log after the call is "Successfully returned from `URLOfEndpoint` or `command`"
    - All calls to `Invoke-RestMethod`, `Invoke-WebRequest`, `Invoke-Expression`, `Invoke-Command` should support the following parameters if needed

## Example Logging Patterns

### `Invoke-RestMethod`

```powershell
Write-PSFMessage -FunctionName $fn -ModuleName $mn -Level Debug -Message "Calling <URLOfEndpoint>" -Tag 'RestCall'
$response = Invoke-RestMethod -Uri <URLOfEndpoint> -Method GET
Write-PSFMessage -FunctionName $fn -ModuleName $mn -Level Debug -Message "Successfully returned from <URLOfEndpoint>" -Tag 'RestCall'
```

### `Invoke-Command`

```powershell
Write-PSFMessage -FunctionName $fn -ModuleName $mn -Level Debug -Message "Calling Invoke-Command on $computerName" -Tag 'InvokeCommandCall'
Invoke-Command -ComputerName $computerName -ScriptBlock { <scriptBlockToRun> } -Credential $credential.ToString() $(if($useSSL){ ' -useSSL '})") + $(if ($useSelfSignedCert) { ' -SessionOption $(New-PSSessionOption -SkipCACheck -SkipCNCheck -SkipRevocationCheck)' }))
Write-PSFMessage -FunctionName $fn -ModuleName $mn -Level Debug -Message "Successfully returned from Invoke-Command on $computerName" -Tag 'InvokeCommandCall'
```
