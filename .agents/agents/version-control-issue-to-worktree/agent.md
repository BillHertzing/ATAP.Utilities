## Step 5: Create Worktree

Run via `terminal`:

```powershell
$repoRoot        = git rev-parse --show-toplevel
$repoParent      = Split-Path $repoRoot -Parent
$repoName        = Split-Path $repoRoot -Leaf
$kebabShortTitle = (<first 6 words of issue title, lowercased and hyphenated>)
$branchName      = "<issueNumber>-$kebabShortTitle"
$worktreePath    = Join-Path $repoParent "$repoName-wt-<issueNumber>-$kebabShortTitle"

git worktree add -b $branchName $worktreePath main
```

## Step 6: Replicate Junctions

**Skip this step if `$repoName` is `SharedVSCode`.** SharedVSCode is the source of
junctions for all other repos and must not have junctions itself.

**Junction target strategy:**

- **Sprint worktrees** (branch name includes `sprint-NNNN`): junctions must point to the
  active SharedVSCode **sprint** worktree (for example, the current
  `C:\Dropbox\whertzing\GitHub\SharedVSCode-wt-64-Sprint-0015-work-items` target),
  not the main worktree. Use `-DevSourceRepoPath` for this.
- **Normal issue worktrees**: junctions point to the SharedVSCode **main** worktree
  (default behavior — just copy targets from the source repo).

> **Junctions vs. rendered configuration (clarified 2026-07-14, DR program item DRR-005):**
> `Set-WorktreeJunctions` remains in use for worktree *structure* (shared folders such as
> `.vscode` and other junction targets). AI-agent configuration surfaces, however, are no
> longer materialized by junctions: the `.ai` folder in SharedVSCode is the canonical
> source and `Render-AIAdapters` renders concrete per-agent files into each repo.
> SprintStartAgent/SprintEndAgent retarget those rendered surfaces at sprint boundaries.
> During the transition a repo may still show either form; do not add new junctions for
> agent-config folders.

Ask the user:
> "Does this worktree need junctions to point to a specific SharedVSCode sprint worktree
> (e.g., for sprint branches where `.claude` / `.github` / `.vscode` should come from
> the sprint instead of main)? If so, provide the full path to the SharedVSCode sprint
> worktree."

**For sprint worktrees** (user provides ShareVSCode sprint worktree path):

```powershell
Set-WorktreeJunctions `
  -SourceRepoPath $repoRoot `
  -WorktreePath $worktreePath `
  -DevSourceRepoPath '<SharedVSCode sprint worktree path>' `
  -DevSourceRepoFolderNames @('.claude', '.github', '.vscode')
```

**For normal issue worktrees** (no dev source override):

```powershell
Set-WorktreeJunctions -SourceRepoPath $repoRoot -WorktreePath $worktreePath
```

Set `junctionsStatus`:

- `"ok"` — command succeeded (exit code 0)
- `"skipped"` — `Set-WorktreeJunctions` not found on PATH, or repo is `SharedVSCode`
- `"error"` — command failed

**Junction safety reminder:** When this worktree is later removed, always run
`Remove-Item -LiteralPath $junctionPath` (NO `-Recurse`) for each junction BEFORE calling
`git worktree remove`. Never remove a parent folder with `-Recurse` while junctions exist
inside it.

## Step 6a: Apply SharedVSCode Context

**Never directly edit `.git/config`, `.gitattributes`, `.gitconfig.shared`, or
`core.hooksPath`.** All Git plumbing mutations flow through the SharedVSCode
PowerShell module.

Run via `terminal`:

```powershell
Import-Module ATAP.Utilities.BuildTooling.PowerShell -Force

$workspaceFiles = @(Get-ChildItem -Path $worktreePath -Filter '*.code-workspace' |
    Select-Object -ExpandProperty FullName)
```

If no `.code-workspace` file exists, set `sharedVSCodeContextStatus = "skipped"` and
warn the user.

Ask the user whether this is normal product work or SharedVSCode validation work.

**Normal product work (default):**

```powershell

```

**SharedVSCode validation work** (user provides the sprint worktree name):

```powershell

  -WorkspaceFiles $workspaceFiles `
  -TemplateRef '<SharedVSCode sprint worktree name>' `
  -Profile 'sprint-NNNN'
```

Verify with:

```powershell
Get-SharedVSCodeContext -WorkspaceFiles $workspaceFiles
```
